# ADR — Inventory Reservation Transactional Lock

**Decision:** The existing machine `revision` + `compare-and-swap` (CAS) mechanism (`machine_instances.revision` update with `WHERE ... revision = expected`) provides sufficient transactional fencing for the basic inventory reservation/release path. Additional separate transactional locks (e.g., `SELECT ... FOR UPDATE`) are not required for the first inventory-release gate, but must be documented and added before claiming full inventory-correctness (e.g., concurrent checkout for the last unit with guaranteed no oversell).

**Rationale:** The current generic machine engine commits state transitions atomically through `commitTransition` (`packages/server/src/domains/machines/adapters/postgres.ts` line 68-103). This uses `UPDATE ... SET revision = expected + 1 WHERE ... revision = expected` inside a `db.transaction`. For the inventory-reservation slice, this provides atomic state-change confirmation. If concurrent checkout commands race against the same item, exactly one transition commits (the one with the matching expected revision); the second receives a `409` conflict. This is verified by the existing real-Postgres concurrency tests (`test(persistence)` commit `0970b80`).

**Limitations:** This CAS approach verifies that exactly one reservation succeeds, but does not independently lock the `quantityAvailable` value across the full inventory aggregate (e.g., if quantity updates span multiple machine instances). A separate `SELECT ... FOR UPDATE` or conditional inventory update is required for full inventory-correctness claims. This ADR documents that limitation explicitly: the current inventory mechanism passes basic concurrency (no duplicate reservation, stale revision rejected) but does not claim full oversell prevention without the additional lock.

**Next step (separate gate):** Before claiming full inventory-correctness, add the additional transactional lock (`SELECT ... FOR UPDATE` on inventory aggregate or conditional update with quantity fencing) and verify through concurrent real-Postgres tests.
