feat(cluster): one confirmed command for identity bootstrap, plus the seed Job

Answers "is the manual sequence right, or should it run automatically?" with: neither.
Re-issuing identity mints new org/project/client IDs and invalidates every token, so
it must never happen as a side effect of bringing things up. But the four manual
steps were the actual error surface - and the ordering is exactly what fails
(seeding before identity exists; forgetting to regenerate the Secret, which produces
a green pod that cannot reach anything).

scripts/k8s-identity.ps1 -Yes:
  1. kubectl port-forward svc/zitadel 8080, waiting for
     /.well-known/openid-configuration rather than assuming it is up
  2. pnpm init:zitadel (re-issues identity; rewrites .env, wrangler.toml, oidc.json)
  3. scripts/cluster-env.mjs + Secret refresh - the step people forget
  4. rollout restart api + worker so they pick up the new IDs
  5. the seed Job, which drives the HTTP API and therefore needs 2-4 to have happened
  6. k8s-status.ps1, where `seed data machine_definitions=2` finally turns green
  Port-forward is opened and closed by the script. Without -Yes it prints what will
  change and exits 2.

deploy/jobs/seed.yaml: the seeder is an API client, not a DB script, so it runs as a
Job against http://api:3000 after the API is Ready. Deliberately not applied by
k8s-up.ps1 - seeding writes demo content and is not part of convergence.

Runbook section 9 records the three options and why the middle one wins, including the
eventual in-cluster bootstrap Job and its two real blockers: init:zitadel writes host
files (ENV_FILE override exists, but the output must become a Secret patch, needing
kubectl + RBAC in the Job) and the machine key/PAT would need mounting.

All three scripts parse with zero errors; the identity guard verified (exit 2).
