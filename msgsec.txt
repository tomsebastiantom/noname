refactor(deploy): extract dev credentials and storage class out of base

`base/` is now credential-free: 18 credential sites and 3 storage-class declarations
moved into `deploy/overlays/local/`. The shape stays environment-neutral; the values do
not.

  base/                      references keys by name (valueFrom.secretKeyRef)
  overlays/local/secrets.yaml  the dev values, in one Secret: noname-infra-secrets

URLs and hosts (postgres:5432, zitadel:8080, api:3000) stay in base on purpose - that is
the wiring, not the environment. What differs per environment is credentials, storage
class, replicas, ingress and image tags.

Three traps surfaced, all now in the runbook's failure catalogue:

1. ZITADEL ignores ZITADEL_MASTERKEY unless `--masterkeyFromEnv` is passed, and exits with
   "no master key provided". Because args cannot reference secretKeyRef, the flag is the
   only way to keep the key in a Secret. Verified afterwards by re-running the identity
   Job: it provisions against the existing database, so a mismatched masterkey would have
   failed there.

2. A *bound* PVC cannot have `storageClassName` removed - "spec is immutable after
   creation". So base omits it and the local overlay adds it back with a JSON6902 patch;
   otherwise every apply fails on all three claims.

3. Moving credentials into secretKeyRef changes a Job's pod template, and a Job template is
   immutable. `keto-migrate`, `s3-init` and `migrate` had to be deleted and re-applied.
   All three are safe to re-run: `migrate up`, and a bucket existence check.

The keto config is a ConfigMap, which cannot hold a credential, so its inline `dsn:` was
removed and the DSN now arrives through the env var the adapter already preferred.

Verified: `kubectl apply -k deploy/overlays/local` clean, all Jobs Completed,
`node scripts/k8s.mjs status` -> all checks passed (exit 0), and `identity --yes` still
provisions correctly against the existing ZITADEL database.
